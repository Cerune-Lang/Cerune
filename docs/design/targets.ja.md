# 出力経路とターゲット

[English](targets.en.md)

この文書では、Ceruneが生成する成果物について、出力経路、ターゲット、成果物、バックエンドを区別します。

この区別は、同じCeruneプログラムから得られた観測結果を正しく識別し、新しいCPU命令セットや実行環境を追加できる状態を保つために必要です。

## 用語

### 出力経路

出力経路は、Cerune IRからどの種類の表現を生成するかを示します。

現在の出力経路には、C、LLVM IR、QBE IR、WebAssembly Text、ネイティブアセンブリ、ネイティブオブジェクト、Cerune bytecodeがあります。

Nativeは[HIR→MIR→x86-64 LIR](native-mir.ja.md)を通ります。MIRは共有の実行表現であり、新しいOSターゲットではありません。

### 直接実行

`run`／`run-ir`の[IR Executor](ir-executor.ja.md)は、完成済みCerune IRを直接実行する経路です。新しい成果物を生成せず、ターゲットABIの選択も行いません。出力経路の表とは別に扱います。`run-vm`はBytecode → VMです。`run-mir`は[独立したMIR実行器](mir-executor.ja.md)で、HIR→MIRを経て実行します。`emit-mir`はその表現を観測する操作です。

`run-mir --ssa`はSSAを直接評価します。LIRはNative生成の内部段階で、`run-lir`やLIR専用の観測コマンドはありません。[段階別の現状](development-status.ja.md)を参照してください。

### ターゲット

ターゲットは、成果物が前提とする実行環境を示します。必要に応じて、次の要素を持ちます。

- 命令セットアーキテクチャ: `x86_64`、`riscv64`、`wasm32`など
- 実行環境: Windows、Linux、bare-metalなど
- ABI: Windows x64、System V、RISC-V LP64Dなど
- 機能: RISC-VのM、A、F、D拡張など

出力経路によっては、Ceruneがターゲットを指定しません。たとえば、Cソースをどの環境向けにコンパイルするかは、外部のCコンパイラを呼び出す側が決定できます。

### 成果物

成果物は、観測可能な実際の出力です。Cソース、LLVM IR、アセンブリ、Cerune bytecodeなどが該当します。

成果物の形式には、アセンブリ構文やファイル形式などの属性が含まれる場合があります。アセンブリという同じ種類の成果物でも、GNU AT&T構文とIntel構文は異なる形式です。

### バックエンド

バックエンドは、Cerune IRを特定の出力経路およびターゲット向けにloweringし、成果物を生成する内部実装です。

バックエンドは実装上の構成要素です。出力経路、ターゲット、成果物をまとめて指す用語としては使用しません。

動的配列`[T]`は現在IR Executor・MIR Executor・Bytecode VM・生成C・LLVM・QBE・WAT・Windows/Linux ASM・自前COFF/ELFで実行できます。[対応範囲](owned-arrays.ja.md)を参照してください。

## 実行経路の責務

IR・VM・NativeはCeruneが完成成果物と実行契約を定義する経路です。C・LLVM・QBE・WATと将来のLean等はemit-onlyで、外部でのビルド・実行・証明検査は利用側が管理します。生成結果の意味を守る責任はCeruneに残ります。

[経路図とbuild / releaseの計画](owned-routes.ja.md)は将来の操作を含みます。以下の表は現行の出力です。

## 現在の構成

現在の出力は、次のように整理できます。

| 出力経路 | ターゲット | 成果物 |
| --- | --- | --- |
| C | Ceruneでは指定しない | Cソース `.c` |
| LLVM IR | 未指定、または明示的なWindows x64 / Linux x86-64（文字列・実行時検査では必須） | LLVM IR `.ll` |
| QBE IR | 未指定、または明示的なWindows x64 / Linux x86-64（文字列では必須） | QBE IR `.ssa` |
| WebAssembly Text | WebAssembly | WAT `.wat` |
| ネイティブアセンブリ | x86-64、Windows / Linux、各OSの呼出規約 | GNU形式のアセンブリ `.s` |
| ネイティブオブジェクト | 明示的なWindows x64 / Linux x86-64 | COFF `.obj` / ELF64 `.o` |
| Cerune bytecode | Cerune VM | Cerune bytecode `.cebc` |

「Ceruneでは指定しない」は、実行中のホスト環境から暗黙に推測することを意味しません。Ceruneの観測結果にターゲット固有の決定を含めず、後続ツールを呼び出す側がターゲットを決めることを意味します。

### QBEの検証バージョン

CIでは[QBE 1.3](https://c9x.me/compile/releases.html)を公式SHA-256で検証して使用します。Linuxは`amd64_sysv`、Windowsは`amd64_win`で実行比較します。WindowsではQBE本体をMinGW/UCRTでビルドし、生成ASMをClang/MSVCでリンクします。ツール自身のビルド環境と生成プログラムのターゲットは別です。

Windows向けの出力・診断・引数の扱いと、段階ごとの検証は[QBE Windows対応](qbe-windows.ja.md)にまとめています。

## 生成物を利用する側との境界

出力経路が存在することと、その経路がすべての言語機能に対応することは別です。文字列は現在すべての経路で生成できます。LLVMとQBEでターゲット指定がない場合は、未使用の定義も含めてlowering前に診断します。意味検証の成功を、各経路の生成成功と混同しません。

LLVMの`--target`は`x86_64-unknown-linux-gnu`または`x86_64-pc-windows-msvc`を選び、成果物に`target triple`を残します。文字列がある場合、Windowsの標準出力をバイナリモードにする判断に使います。未指定で文字列を使う場合はソース位置付きで診断し、ホストから補いません。数値だけでも実行時検査を持つ場合は、診断のWindows/Linux ABIを選ぶためにターゲットが必要です。表現と初期化の詳細は[文字列の設計](strings.ja.md#llvmでの表現とターゲット)を参照してください。

生成物の比較では、次の問いを分けます。ここでいう対応状況は情報であり、外部プログラムを起動する許可ではありません。

QBEは明示的な`x86_64-unknown-linux-gnu` / `x86_64-pc-windows-msvc`と、下流の`amd64_sysv` / `amd64_win`をそれぞれ組み合わせます。直接アセンブリはWindows/Linux x86-64を明示的に選べ、WATはWebAssembly固定で、WATの文字列出力はバイト値を受け取るホスト関数との契約です。経路ごとの格納・出力の違いは[文字列の設計](strings.ja.md)に残します。

次の担当表は、現行のemit成果物を利用側が処理する場合です。計画中のCerune-owned buildでは、完成成果物を作るためのツール・依存条件の管理をCeruneが担当します。

| 問い | 確認する内容 | 担当 |
| --- | --- | --- |
| 生成できるか | Ceruneの版が、その出力経路とターゲットに対応するか。個々のソースのエラーは生成時に診断する | Cerune |
| ビルドできるか | 対象に合うコンパイラ・アセンブラ・リンカ・必要なライブラリが揃うか | 利用側 |
| 実行できるか | CPU・OS・実行時ライブラリ・ホスト関数などの条件が揃うか | 利用側 |
| 実行してよいか | 利用者の許可と、実行環境の制限を満たすか | 利用側の実行ポリシー |

外部ツールが見つかるだけでは、ビルドや実行の成功は確定しません。事前の確認結果と実際の各段階の結果を分け、未対応、必要なツールの不足、権限による拒否、生成失敗、ビルド失敗、実行失敗、時間切れを区別します。実行できなかった経路を比較対象から黙って消したり、成功として数えたりしません。

Ceruneを動かす環境と生成物のターゲットも別です。WSLで`emit-asm`を呼んでも、出力はWindows x86-64向けのGNU AT&T構文です。Linux向けASMは`--target x86_64-unknown-linux-gnu`で明示的に選べます。Windows向けでも、Cerune内部の集約値の受け渡しは外部C ABIとの互換性を保証しません。

### 比較で確認できること

現行CLIの`run`／`run-ir`はIRを直接実行し、`run-vm`はVMで実行し、`emit-*`は成果物を返します。これを利用した終了状態や標準出力の比較に、新しい公開APIは必須ではありません。`.cebc`をVMで読み込んで実行するCLIはありません。

標準出力の一致は表示結果の一致です。浮動小数点のNaNの内部ビットなど、表示に含まれない情報まで一致した証拠にはなりません。ビット単位の比較が必要になった場合は、別途、型付きの観測形式を設計します。数値の許容誤差、改行の正規化などを使う場合も、比較条件として明示します。

VMの結果だけを正解とはみなしません。既知の期待値や言語規則に対するテストも残します。また、両方が非ゼロ終了しただけでは、同じ理由で停止したとは判断できません。生成・ビルド・実行のどこで失敗したかと、それぞれの診断を保持します。

### 記録と安全性

利用側は、入力と生成物を識別できる情報、Ceruneのビルド識別情報、出力経路、実際のターゲット、外部ツールの版と明示的なオプション、段階ごとの結果、比較条件を記録します。`cerune --version`でパッケージの版を取得できます。同じ版番号の開発ビルドを区別する場合は、検証したコミットや実行ファイルのハッシュも記録します。対応出力先を機械可読形式で列挙する機能は未実装です。公開スキーマが必要になった時点で、実際の利用箇所をもとにバージョン化して定義します。

生成物や観測データに含まれる文字列を、実行コマンドや許可として解釈しません。生成コードの実行は観測データを読むこととは別の操作です。利用側で信頼済みのツールと引数を選び、未信頼コードは適切な隔離環境で実行します。時間制限や別プロセス化だけを安全な隔離とみなさず、出力サイズも制限します。ソース本文・パス・環境変数全体を無条件に記録しません。

## 観測結果の識別

ターゲットが成果物へ影響する場合、観測結果は少なくとも次の条件によって識別されます。

- Ceruneのバージョン
- ソース入力
- 出力経路
- ターゲット
- ターゲット機能
- 明示的なオプション

これらの条件が同じであれば、Ceruneは決定的な観測結果を生成します。

ターゲット情報を成果物自体へ埋め込む必要はありません。ただし、CLIの呼び出し条件や付随するメタデータから、その成果物を生成した出力経路とターゲットを識別できる必要があります。

ホストOS、ホストCPU、環境変数などから暗黙にターゲットを選択すると、同じ明示的な入力から異なる結果が生じます。Ceruneは、観測結果へ影響するターゲット条件を暗黙に決定しません。

## loweringの境界

Cerune IRは、出力経路とターゲットに依存しない意味を保持します。

次のような決定は、バックエンドへのlowering後に行います。

- 命令の選択
- レジスタの利用
- スタックフレームの配置
- 値のサイズ、配置、アラインメント
- 関数呼び出し規約
- ターゲット機能に応じた命令の利用
- アセンブリ構文および成果物形式

ターゲット固有のIRは、各バックエンドの内部境界として保持できます。すべてのターゲットが共有する汎用マシンIRを導入する必要はありません。

## 新しいターゲットの追加

新しいターゲットを追加する場合は、次の性質を保ちます。

- ターゲットを安定した識別子で区別できること
- 対応する出力経路とターゲットの組み合わせが明示されること
- ターゲット固有の決定がCerune IRへ入り込まないこと
- 対応していない組み合わせを診断として報告すること
- ターゲット機能を決定的な順序と形式で扱うこと
- 同じ明示的な条件から同じ成果物を生成すること

ターゲットの追加は、新しい権限を観測APIへ与えるものではありません。ターゲット識別子はlowering条件を選択するデータであり、外部コマンドを実行する権限やコンパイラ内部を書き換える権限ではありません。

外部アセンブラ、リンカ、コンパイラの選択と実行は、Ceruneの成果物を利用する側の責務です。

機械語を含むオブジェクトと実行ファイルの生成・観測は[ネイティブコード](native-code.ja.md)を参照してください。
