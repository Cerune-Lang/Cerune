# Evaluating WAT input storage splitting and coalescing

[日本語](wat-input-storage.ja.md)

## Decision

**Keep existing free-storage reuse; do not adopt these splitting/coalescing prototypes in the product.** This completes the current input-capacity decision for #154. Broader memory-efficiency work remains in #133.

Splitting alone increased pages over repeated input. Coalescing prevented that growth but did not reduce pages below the current implementation in these measurements. Preserving input semantics during compaction does not itself establish a memory-footprint improvement.

The [previous improvement](input-compaction.en.md) for Rust/C/LLVM/QBE/Native remains in place.

## Compared policies

The baseline is PR #167 merged as `b6bae24`. Tests modify WAT generated by the product emitter.

| Policy | Behavior |
| --- | --- |
| Current | Reuse released string blocks at their existing capacity |
| Split only | For valid lines at most half the requested limit and at least 4096 bytes shorter, align retained capacity to eight bytes and split the remainder into a free block |
| Split + coalesce | Also merge physically adjacent free string blocks on final owner release |

A split leaves a 24-byte ownership header and at least eight payload bytes. Coalescing requires both blocks to be free and their addresses contiguous. Accounting by string length is unchanged.

## Measurements

Read eight distinct two-byte lines with a 1 MiB limit, retain and print them, then release all; repeat three times. Node on Windows and Linux/WSL produced the same results. A page is 64 KiB.

| Policy | Live payload capacity with eight lines | Pages after full release in each cycle |
| --- | ---: | --- |
| Current | 8,388,608 bytes | 129 → 129 → 129 |
| Split only | 64 bytes | 129 → 257 → 385 |
| Split + coalesce | 64 bytes | 129 → 129 → 129 |

Allocating and retaining a dynamic array after each line produced the same page progression. Arrays share the allocation cursor with strings but have a separate owner list. Coalescing does not cross array storage. Tests also verify one coalesced free string block after full release without array gaps, versus eight blocks with gaps.

A split remainder cannot satisfy the next 1 MiB reservation. Live short strings separate the blocks, so coalescing cannot avoid the initial additional allocations while retaining eight lines. Coalescing after full release benefits the next cycle, but does not reduce pages already grown.

This is a capacity evaluation at a fixed input scale, not an RSS/speed benchmark or proof that no workload benefits. The prototype repeatedly scans the list; its complexity has not been validated as a production allocator.

## After invocation storage was introduced (PR #197)

The initial measurements above used fixed-address temporaries. With per-invocation frames, a retained frame block separates the first string from the remaining seven even without arrays. The prototype merges free string blocks only; it cannot cross separately managed frame storage.

| Split + coalesce case | String blocks after full release | Total free payload capacity | Largest free payload capacity |
| --- | ---: | ---: | ---: |
| No arrays | 2 | 8,388,752 bytes | 7,340,176 bytes |
| Array retained after each line | 8 | 8,388,608 bytes | 1,048,576 bytes |

Page progression, input operations, and output remain as reported above, so the decision not to adopt the prototype is unchanged. Besides checking block counts and capacities, tests require that no adjacent free string blocks remain after coalescing. Frame and array storage is not included in free string capacity.

## Semantics and observation checks

- Compare output, consumed bytes, and read/write/flush traces across plain output, measurement-only output, and both prototypes; also compare with IR Executor results.
- Change the limit in [retained_lines.ceru](../../examples/stdin/retained_lines.ceru) to 1 MiB inside tests; cover Japanese, NUL, CR/LF, combining characters, an unterminated final line, EOF, and subsequent invalid UTF-8.
- With memory capped at 17 pages, the second reservation fails with identical diagnostics, source origin, prior output, and consumption.
- Check block overlap, list cycles, alignment, length versus capacity, and accounted bytes versus live string lengths inside the test artifacts.
- Pass only numeric observations to the host. Do not expose memory or a new operation API. Measurement imports and prototype functions exist only in test artifacts.

## Reproduction and remaining work

Set `CERUNE_TEST_NODE` and `CERUNE_TEST_WAT2WASM_JS` explicitly to valid tools.

~~~sh
cargo test --test stdin_routes wat_storage_policy -- --nocapture
~~~

Generated WAT/Wasm, input-operation JSON, and capacity CSV are saved under `target/stdin-wat-storage-*` and included in existing CI input-test artifacts. CSV columns are phase (1=successful input, 2=final owner release), accounted bytes, live payload capacity, free payload capacity, owner count, pages, string-block count, and largest free payload capacity.

Reducing pages requires comparing approaches such as extending/reusing a terminal free block for the next reservation or moving a completed line into smaller storage. Such a design must cover the cursor shared with arrays, zero consumption before allocation failure, owner movement, and search cost. These remain #133 candidates rather than changes adopted here.

The time and call count of one-byte OS reads are a separate performance topic. Batched reads affect hidden read-ahead and consumption contracts, so measurement and input-contract design must precede that work.
