# WAT入力領域の分割・再結合の評価

[English](wat-input-storage.en.md)

## 判断

**現行の空き領域再利用を維持し、今回の分割・再結合の試作は製品へ入れません。** #154の入力容量の検討は、この判断で一区切りとします。より広いメモリ効率の調査は#133で続けます。

分割だけでは繰返し入力でページ数が増えました。再結合を加えると増加を防げますが、今回の測定では現行実装よりページ数を減らせませんでした。入力の意味を変えずに縮小できることと、実際にメモリ規模を減らせることは別です。

[前段の改善](input-compaction.ja.md)で導入したRust/C/LLVM/QBE/Nativeの縮小は維持します。

## 比較した方式

基準はPR #167統合後（`b6bae24`）です。製品emitterから生成したWATに、テスト内で次の変更を加えました。

| 方式 | 処理 |
| --- | --- |
| 現行 | 解放された文字列領域を、その容量のまま再利用 |
| 分割のみ | 有効な入力行が指定上限の半分以下、かつ4096バイト以上小さい場合、本文容量を8バイト単位に揃え、余りを空き領域へ分割 |
| 分割＋再結合 | 上記に加え、最後の所有者を解放した際、物理的に隣接する空き文字列領域を結合 |

分割には24バイトの所有管理領域と8バイト以上の本文領域を残します。再結合は両側が空きで、アドレスが連続する場合だけ行います。文字列長に基づく使用バイト数は変えません。

## 測定結果

上限1 MiBで、異なる2バイトの行を8本保持・表示・全解放する処理を3回繰り返しました。Windows/Linux(WSL)のNodeで同じ結果です。1ページは64 KiBです。

| 方式 | 8本保持時の本文容量 | 各周期の全解放後のページ数 |
| --- | ---: | --- |
| 現行 | 8,388,608バイト | 129 → 129 → 129 |
| 分割のみ | 64バイト | 129 → 257 → 385 |
| 分割＋再結合 | 64バイト | 129 → 129 → 129 |

各行の後に動的配列を確保して保持するケースでも、ページ数の推移は同じでした。配列は文字列とメモリ末尾を共有しますが、別の所有リストで管理されます。再結合は配列を飛び越えません。配列を挟まない場合は全解放後に空き文字列領域が1本へ結合され、配列を挟む場合は8本残ることも検査しました。

分割後の余りは、次の1 MiB予約には足りません。生存中の短い文字列が間にあるため、再結合しても最初の8本を保持する間の追加確保を避けられません。全解放後の再結合は次の周期には効きますが、既に増えたページ数は減りません。

これは固定した入力規模での容量評価です。RSS・実行速度の測定や、全ワークロードで改善しないことの証明ではありません。試作の再結合はリストを繰り返し走査する簡単な実装であり、製品用allocatorとしての計算量も未検証です。

## 意味と観測の検証

- 通常の生成物、計測だけを加えた生成物、2種類の試作で、出力・入力消費数・read/write/flushの記録を比較。IR Executorの結果とも照合。
- [retained_lines.ceru](../../examples/stdin/retained_lines.ceru)の上限をテスト内で1 MiBへ変更し、日本語・NUL・CR/LF・結合文字・改行なし最終行・EOF・後続の不正UTF-8を比較。
- memoryの上限を17ページにした場合、2回目の予約失敗の診断・ソース位置・それ以前の出力・消費数が一致。
- 領域の重複、リスト循環、整列、本文長と容量、使用バイト数と生存文字列長の一致をテスト内で検査。
- hostへ渡すのは数値だけ。memoryや新しい操作APIは公開しない。計測importと試作関数はテスト生成物だけに追加。

## 再実行と残る課題

`CERUNE_TEST_NODE`と`CERUNE_TEST_WAT2WASM_JS`に有効なツールを明示して実行します。

~~~sh
cargo test --test stdin_routes wat_storage_policy -- --nocapture
~~~

`target/stdin-wat-storage-*`に生成WAT/Wasm、入力操作のJSON、容量のCSVを保存します。CSV列はphase（1=入力成功、2=最後の所有者の解放）、使用バイト数、生存本文容量、空き本文容量、所有者数、ページ数、文字列領域数、最大空き本文容量です。CIでも既存の入力テストartifactに含まれます。

ページ数を減らすには、末尾の空き領域を次の予約で拡張・再利用する仕組みや、小さい完成領域への移動を別途比較する必要があります。配列との共有末尾、確保失敗前の入力消費ゼロ、所有者の移動、走査コストを含む設計になります。今回は採用せず、#133の改善候補として残します。

1バイトずつのOS読取りの時間・呼出し回数も別の性能課題です。まとめ読みは隠れた先読みと消費数の契約に影響するため、容量改善へ混ぜず、実測と入力契約の検討を先に行います。
