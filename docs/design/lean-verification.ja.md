# Leanでの意味の対応とプログラムの証明

[English](lean-verification.en.md)

## 目的

Lean backendでは、次の2つを両立させます。

1. **変換の対応**：完成済みCerune IRと、生成したLeanプログラムが同じ意味を持つこと。
2. **プログラムの性質**：そのプログラムが、明示した前提の下で仕様を満たすこと。

将来Ceruneがself-hostした場合、Ceruneで書かれた処理系も2の対象にできます。
self-hostそのものは正しさの証明ではありません。処理系の仕様、対象とする入力、生成結果の意味を別途定義して証明します。
現在のRust処理系や、Lean以外のbackendまで自動的に証明済みになることもありません。

**現状は設計と小さな検証実験です。公開Lean backend、`emit-lean`、全言語の形式意味論は未実装です。**
[検証実験](../../experiments/lean/README.md)では、実際の`increment: u8 → u8`のHIRと生成Lean、HIRとlowering済みMIRの対応、および利用者の性質を検査します。`choose: u8 → u8`ではifと短絡を追加し、MIRの型付き局所値・命令列・jump／branch／returnを独立に評価します。`advance: u8 → u8`の5例ではwhile／for・可変局所値・循環CFG、if内のbreak／continue、入れ子の最内周への作用、forの初期化・更新・更新時のoverflowを扱います。それぞれ全256入力の値またはoverflowと出自を検証します。heap・一般のloop停止性は証明対象外です。

分岐例のMIR評価ではblock数をfuelにし、exporterが未到達blockも含めた循環を拒否します。各経路がこの上限内で完了することを全256入力の対応定理でも検査します。`completed (.error …)`（言語上の停止）、`invalid`（モデルの不正状態）、`exhausted`（fuel不足）を区別し、fuel不足同士の一致で成功にはしません。ループ例では別の明示上限を使い、単純なwhileはHIR 16文／MIR 11block、break／continue付きは22文／22block、入れ子は28文／23block、forは23文／25block、更新停止例は8文／5blockで全入力が完了することを追加証明します。完了には言語上の異常停止も含み、更新停止例は全入力でoverflowします。反復回数・更新・戻り辺・停止出自、break／continueの飛び先や内側から外側への誤ジャンプ、forの初期化・更新の飛ばし・更新出自の改変、両方のfuelを0にする変更を拒否します。上限は例ごとの値であり、一般のloop停止性や上限探索アルゴリズムを証明したものではありません。

forのHIRは`forLess`として初期化・条件・更新・本文を保持します。モデル内部の`forNext`が初期化後の反復を表し、本文末尾とcontinueは更新を一度通って条件へ戻り、breakは更新を飛ばします。MIRのjump先からHIRを再構成しません。共通の対応・完了定理は`LoopCorrespondence.lean`に置き、実行比較はそこで証明した同じ定義を使います。

SSAも[有限例の検証](mir-ssa.ja.md#leanによる有限例の検証)に対応します。元MIR→SSA→変換後MIRの値・停止出自と明示上限内の完了を、既存7例と合流・入替え例の全u8入力で検査します。SSAの制御は独立モデル、単一演算は既存MIRモデルと共有です。合流・入替えの独立仕様も検証し、対応定理で変換後MIRへ移送します。SSAの定理は標準公理`propext`に依存します。一般のSSA変換・heap・Nativeまで証明したとは扱いません。

## 接続する契約

```text
Cerune source → 共通frontend → 完成済みCerune IR
                                  ├─ Lean上のIRモデル（参照する意味）
                                  └─ Lean生成結果 ＋ 変換対応の証明
                                            └─ 利用者の仕様 ＋ 性質の証明
```

概念的には、有効な入力・状態sに対し
`observe(evalIR(P, s)) = observe(evalLean(emit(P), encode(s)))`
を変換対応の契約とします。
さらに生成プログラムが性質Qを満たすことを証明し、対応の定理を使ってIR側の性質へ移します。
同じ生成関数を両辺に置くだけの恒等式や、成功例の出力一致だけでは、この契約を満たしません。

参照モデルは既存の`ir::Program`の意味を形式化します。
別の言語・別のfrontendを作ったり、名前解決・generic・match・所有展開をLean側でやり直したりしません。
ただし、Rustデータ構造をLeanの項へ写す境界と、モデルが既存仕様に合っていること自体は監査・検証が必要です。

## 実行時意味論

観測には戻り値だけでなく、出力バイト列、停止コード、NodeId・SourceId・Span、停止までの出力を含めます。
途中状態や資源予算を扱う証明では、その状態も関係へ含めます。

| 項目 | 保つ意味 |
| --- | --- |
| 整数 | 各型の範囲、桁あふれ、除算・シフト・明示変換の失敗。無制限整数や折り返し演算へ黙って置換しない |
| 浮動小数点 | IEEEの幅、丸め、NaN・無限大・負のゼロと変換規則。Leanの実数へ置換しない |
| 文字列 | 不変のバイト列、日本語・NUL・CR/LF、非正規化、表示と比較 |
| 制御 | 左からの評価、短絡、関数、ループ、break / continue / return |
| 複合値・所有 | コピー後の独立性、共通IRに現れる確保・retain・release・解放と予算 |
| 外部条件 | 将来のI/Oや実際の確保失敗は環境条件を明示。理想化したheapの証明をOS動作の保証としない |

有限fuelでの一致は、そのfuelまでの一致です。一般的な停止性や無限実行まで保証したとは扱いません。
全域の実行結果を語る段階では、停止性の証明か、発散を含む実行関係が必要です。
資源上限によるCeruneの停止と、証明器・テストの時間切れも区別します。

## backendと検証器の境界

Leanは[emit-only](owned-routes.ja.md)です。将来の`emit-lean`はLeanソースと追跡情報を生成し、Leanの起動を通常のCerune CLIへ内包しません。
開発用テスト・CIでは、版を固定したLeanを起動して生成コード・定理を検査します。

最初はプログラムごとの対応証明を検査するtranslation validationを採用します。
失敗した証明を成功に変更するfallbackは置きません。将来、変換アルゴリズム一般の正しさを証明する場合は、別の成果として追加します。
利用者の性質は別ファイルで宣言し、生成器が仕様を書き換えて通せない構成にします。
証明用の生成物と実行する生成物を別々に改変せず、同一の定義を参照させます。

ソース、完成IR、生成定義、定理、対応表、意味論とLeanの版を検査結果に結び付けます。
型・値・所有の一部を未対応のまま削除して証明済みとしません。
未使用の定義を含む全体を受け付ける場合も、対応範囲を先に検査します。
関数だけを検証する実験なら、選択した関数と、証明していない呼出側を明示します。

## テストと証明を分ける

- 既知の期待値と、IR Executor・VM・各生成経路の実行結果を比較する。
- Leanモデルと生成結果の対応を証明し、前提を含む定理の文面を確認する。
- 利用者が書いた性質を、同じ生成定義に対して証明する。
- 生成結果、失敗の出自、仕様を意図的に変更し、検査が拒否することを確認する。
- 未対応・未実行・時間切れ・証明失敗を区別し、成功に数えない。

Lean kernelの受理も、定理の文面と利用した公理を前提にした保証です。
`#print axioms`で依存を確認し、`sorryAx`、独自の未検証公理、native評価による追加の信頼を通常の証明成功へ混ぜません。
incrementのHIR→Leanと性質の4定理、および分岐例の独立した仕様の定理は公理依存が空です。incrementのMIR関連3定理・分岐例の対応と移送2定理・各ループ例の対応／完了／独立仕様／移送4定理はLean標準の`propext`に依存します。ループモデルにframeを加えた今回の定義では、既存のループ仕様定理にもこの依存が現れます。`decide`で得た証明をkernelで検査し、公理一覧を完全一致で検査します。`native_decide`や独自公理には依存しません。
[Leanの証明検証](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)と[公理の説明](https://lean-lang.org/doc/reference/latest/Axioms/)を参照してください。

## 段階と完了条件

| 段階 | 内容 | 完了条件 |
| --- | --- | --- |
| 実装済みの実験 | incrementのHIR→LeanとHIR→MIR、chooseのif・短絡・非循環CFG、advanceのwhile／for・可変局所値・if内のbreak／continue・入れ子・初期化／更新・循環CFGと明示上限内の完了 | u8全入力の対応・性質と、値・出自・戻り先・分岐先・短絡・条件・更新・戻り辺・評価上限・仕様の改変拒否を検査。個別snapshotの証明で、変換アルゴリズム一般の証明ではない |
| backendの基盤 | 共通IRの取り込み、出自、結果・trace、生成定義と利用者の仕様の分離 | `emit-lean`の契約と対応表を確定し、既存テストから正常・異常例を移植 |
| 制御と数値 | 全整数・真偽値・評価順・関数・分岐・ループ、明示変換 | 値だけでなく失敗・先行出力・停止条件を照合。floatは別の明示モデルで追加 |
| 複合値と資源 | 文字列、配列、構造体、直和、所有・予算 | 既存の意味論と同じ機能範囲を目標にし、差を対応表で追う |
| 利用者の証明 | 事前・事後条件、不変条件、必要に応じた停止性 | source → IR → Leanの対象と前提を追跡できる例を追加 |
| self-host後 | 処理系をCeruneプログラムとして検証 | frontend・IR変換・各backendごとの仕様と証明、bootstrapの信頼境界を明記 |

小さな実験の範囲を、最終的なLean経路の言語サブセットとして固定しません。
この実験が通っても、RustのIR構築・実行器・生成器全体や、Native出力まで証明したことにはなりません。
