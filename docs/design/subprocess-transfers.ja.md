# 子プロセスの進行中転送と取消し

[English](subprocess-transfers.en.md)

[子プロセス契約](subprocesses.ja.md)の転送部分を具体化した文書です。[OS試作](../../experiments/subprocess/README.md)で、複数streamの転送が進行中のまま期限や失敗に到達することを確認しました。

## 現在の実装と責務

| 部品 | 状態と責務 |
| --- | --- |
| [`Transfers`](../../src/runtime/process/transfers.rs) | 実装済みのRust状態管理部品。転送の識別、buffer所有、取消し、確認済み受理数、部分出力、再利用条件を検査 |
| [状態遷移テスト](../../src/runtime/process/transfers/tests.rs) | OSを起動せず、応答順序・競合・不正応答を注入して検証 |
| `Processes::run` / `Backend` | 接続済み。所有権付き転送、期限、終了監視、取消し、有限の後始末を共通runtimeで制御 |
| 実OS接続 | [Windows Backend](subprocess-windows.ja.md)を接続済み。Linuxは専用監督の接続が後続 |
| 言語API・IR・各経路 | 未実装。新しい実行経路や独自の言語意味論は追加しない |

`Transfers`単体は起動・時計・OS資源回収を実行せず、接続済みの`Processes`が`Backend`へそれらを要求します。Rust APIはWindows実OS接続で利用しますが、言語の公開APIではありません。

## 転送の単位と所有

1呼出しに一つの`Transfers`を作り、接続内で再利用しない非0の呼出し番号を渡します。転送番号は呼出し内で単調増加し、桁あふれ時は新しい転送を拒否します。番号を巻き戻しません。

| 項目 | 規則 |
| --- | --- |
| 同時実行 | stdin、stdout、stderrに各1操作まで。同じstreamの次の操作は前の終端通知後 |
| stdin | 未受理部分の先頭を最大4096バイトずつ送る。全量の受理を確認した後でcloseを別操作として行う |
| stdout/stderr | 各stream内の順序を保持。stream間のバイト順は定義しない |
| 読取り上限 | 保持上限までの残り＋最大1バイトを要求し、1回は最大4096バイト。超過検出バイトは読取り数に含め、結果本文には含めない |
| 起動前の確保 | 両出力の保持上限と、3個の4096バイトbufferを検査・確保。足し算のoverflowと容量不足は`OutputBudget`、確保失敗は`AllocationFailed` |
| bufferの寿命 | `Transfer`を接続へ移す。OSが参照しなくなるまで接続が所有し、終端通知と一緒に返す |
| 結果の寿命 | 部分stdout/stderrは`Settlement`へ所有権を移す。未完了bufferは接続が引き続き所有 |

bufferの複製・拡張APIはありません。所有権の移動で内部アドレスは変わりません。ただし、Rustの型だけでOSの参照終了を検出することはできません。接続は参照終了を確認してからbufferを返す責務を持ちます。上限は要求したバイトbuffer容量であり、allocatorの管理領域やCeruneの配列領域を含む物理メモリ保証ではありません。

## 状態遷移

| 操作 | 遷移・意味 |
| --- | --- |
| `prepare_*` | `Prepared`。bufferを準備しただけで、外部転送は未実行 |
| `submit(ticket)` | 外部submitの直前に`Submitted`へ移す。この後は外部の進行があり得る |
| `withdraw(transfer)` | `Prepared`だけを回収して`Terminal`へ移す。停止後も可能。外部への効果はない |
| `complete(transfer, n, result)` | `Submitted`の終端通知。確認済み数を反映して`Terminal`へ移す |
| `stop(failure)` | 最初の失敗を保持し、新しいprepare/submitを停止。進行中の操作やbufferを消さない |
| `request_cancel(ticket)` | 停止後の`Submitted`について一度だけ取消し要求を作る。重複要求は新たな外部操作を要求しない |
| `cancel_reply(ticket, reply)` | 要求受理・間に合わなかった・要求失敗を記録。転送の終端通知ではない |

`submit`はOSへの提出成功を意味しません。提出できなかったと確定した場合は`NotSubmitted`、提出状態が不明なら`Submitted`のまま保持し、停止・取消し・後始末へ進みます。曖昧な応答を「未送信」に変換しません。

取消し応答は転送完了より後に届く場合もあります。取消し後の成功・部分成功・失敗の終端通知は通常どおり数えます。取消し要求が失敗しても、後で届いた転送完了は有効です。

## 終端通知と受理数

`confirmed`は、その操作で確認した受理・読取りバイト数です。stdinについては子が読んだ数を意味しません。

| 終端結果 | 受理数と処理 |
| --- | --- |
| `Done` | 実際の受理数を加算。転送の0バイトは0進行の失敗。stdin closeの0バイトは完了 |
| `Eof` | 読取り専用で0バイト。出力streamの終端を記録 |
| `Failed` | 確認済み部分を残した転送/close失敗 |
| `Cancelled` | 取消し要求済みの操作に限る。確認済み部分を残す。0でもEOFではない |
| `NotSubmitted` | 外部操作が始まっていないと確認した場合だけ。受理数は0 |
| `ProgressUnknown` | 確認できた下限と本文の先頭を残す。それ以上の進行は不明で、接続を再利用しない |

要求量を超える数、別呼出し・古い操作・重複の応答、不正なEOFや取消し通知は契約違反です。重複加算せず接続を再利用不可にします。別streamの有効な終端通知はその後も回収できます。

`Progress.known`は「返却済みの数が総数として確定しているか」を示します。`Submitted`が残っている間はfalseです。有効な終端通知で確定すればtrueへ戻り、`ProgressUnknown`や不正な数が返った場合はfalseを保持します。通知が来ないことを0バイトの確定とは扱いません。

## 期限・後始末・次の呼出し

期限の判定は呼出し側の責務です。期限以上を観測した場合は、先に`stop(Timeout)`を行い、その後に届く終端通知の受理数と本文も反映します。最初の失敗を、後続の転送失敗や後始末失敗で上書きしません。この部品は時計を読みません。

有限の後始末を終えたら`finish(cleanup)`で結果を確定します。接続が報告した回収状態はそのまま残し、次の条件をすべて満たしたときだけ`reusable`をtrueにします。

- 未完了・未回収の準備済み操作がない。
- 各streamの受理数が確定している。
- 契約違反がない。
- 接続から管理範囲・子・ハンドルの後始末完了が報告されている。

失敗のない転送ではstdin closeと両出力EOFも必要です。子の終了状態は、この部品の外で共通runtimeが確認します。失敗後はEOF未到達でも、進行数と資源回収が確定すれば接続を再利用できます。

未完了操作があれば、接続が`Cleanup::Complete`と報告しても再利用不可です。結果には未完了の識別子と未確定の受理数を残します。接続側は未完了bufferとOS管理情報を保有し続けます。`finish`はそれらを解放せず、暗黙の待機・再試行もしません。

## 観測と検証

`snapshot()`は呼出し番号、NodeId/Span/SourceId、上限、操作番号、要求/確認済み/保持バイト数、状態、取消し応答、終端結果、最初の失敗をコピーします。本文は含めず、割当て・時刻取得・I/Oを行いません。操作を進めるAPIとは分離します。`Transfers`は各streamの最新操作だけを保持します。共通runtimeの`events()`には各段階のsnapshotを上限付きで保存し、無効化・容量到達・確保失敗で実行を変えません。`Outcome.transfers`は履歴設定によらず最終状態を保持します。

試験では3streamの全6完了順、取消し応答3種と終端結果の競合、取消し応答の遅着、未通知、部分入力失敗、上限0/ちょうど/超過、0進行/EOF、未知の進行、未提出の回収、二重・別呼出し・古い応答、予算、後始末、観測の有無を検証します。

## 共通runtimeへの接続

`Processes::run`がこの部品を起動・期限・終了監視・後始末へ接続します。呼出し番号を再利用せず、各streamの前操作が終端した場合だけ次の転送を提出します。stdinは確認済み受理数だけ進め、全送信後にcloseを提出します。

接続は`submit`でbufferを所有し、`poll(deadline)`から固定容量の`Batch`を返します。1回で転送終端3件、取消し応答3件、終了状態1件、後始末1件まで受け取ります。同時通知は次の順序で処理します。

1. 時計の逆行、期限到達。失敗を先に記録するが、受け取った通知は捨てない。
2. stdin、stdout、stderrの転送終端。同じstreamの不正な複数通知は番号順で検査する。
3. 取消し応答。転送終端後の応答も同じ操作へ対応づける。
4. 子の終了状態。重複終了やsignal 0は契約違反。
5. 後始末報告。開始前の報告は契約違反。

通常の空通知、期限前の`Deadline`通知も契約違反です。`Interrupted`による再待機は可能です。配列位置を操作順には使わず、本文を取り出す順序と操作を実行する順序を混同しません。

失敗後は新しい転送を提出せず、残る操作へ一度だけ取消しを要求し、`begin_cleanup`を一度呼びます。正常時にも管理範囲を回収します。制御操作は待機せず、後始末中のpollにも別の有限期限を渡します。期限以上で返った通知にも部分結果を反映してから停止します。

`Report.cleanup_reported`は接続の生の報告、`Report.cleanup`は期限・時計を検査した判定です。遅れた完了報告では回収済みフラグを残しつつ期限超過とし、再利用しません。転送が終端していても取消し応答が欠けていれば契約違反として再利用しません。

旧同期モデルは`cfg(test)`内だけに残し、共通ケースの結果を比較します。今回の移行でRustの`Backend`契約は変更しましたが、言語CLI・生成経路の利用契約はまだ導入していません。Windows実OS接続では起動に`CallContext`を渡し、転送前の失敗も呼出し番号・出自へ結び付けます。
