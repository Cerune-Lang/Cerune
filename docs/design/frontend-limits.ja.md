# コンパイル入力の上限

[English](frontend-limits.en.md)

## 目的と範囲

深い構文や大きな依存ファイルを、ソース位置を持つ通常の診断で拒否します。共通frontendで検査するため、実行器・生成先によって判定は変わりません。評価順、型、数値の意味や相対importの解決規則は変更しません。

この上限は処理系の受付条件です。実行時の文字列・配列予算、generic展開やimportの深さとは別です。処理系全体のメモリ・時間・スタック使用量を保証する仕組みではなく、任意の小さなホストスタックでの実行や、外部で組み立てたAST全体の検証も対象にしません。

## 構文と式の深さ

| 検査 | 上限・数え方 | 超過時の位置 |
| --- | --- | --- |
| 開いている区切り | `(`・`[`・`{`の合計16段。閉じた区切りは除く | 上限を超える開きtoken |
| 式の解析の入れ子 | 解析中の式と、その外側で解析中のblockの合計16段 | 次の式を始めるtoken |
| 式のAST | 根から葉へのノード数と外側のblock数の合計32。葉も1と数える | 超過した式のSpan |
| ファイルimportの深さ | 既存どおり128段 | import宣言 |

文字列・コメント内の記号は区切りに数えません。配列要素数や引数数などの幅も、式の深さとは別です。括弧は区切りに数えますが、式のASTへ余分なノードを追加しません。関数本体もblockです。

区切り検査だけでは、開き括弧の前に再帰するmatchの対象式や、`1+1+…`・`a.field.field…`のような深い木を防げません。そのため検査を分けています。単項演算子は反復で読み、右側から組み立てます。式の木は再帰せずに検査し、連続した二項演算・添字・フィールド・単項演算の構築途中でも上限を確認します。巨大な木を完成させてから捨てる実装にはしません。

上限はParser単体に加え、Windows/Linuxのdebug CLIで解析・IR生成まで確認します。式とblockの個別上限を同時に許すと実際の深さが増えるため、外側のblockを合算します。診断を返した後の別コンパイルへカウンタを持ち越しません。

既存の通常exampleは維持します。これまで偶然受理できた深い入力は診断になる場合があります。上限を超える式は、利用者が型付きの中間値や関数へ明示的に分けられます。コンパイラが観測不能な書換えや再結合を行うことはありません。

## ファイルの読込み予算

`modules::load`とCLIの既定値は次の通りです。`modules::load_with_limits`では、呼出し前に明示した`LoadLimits`を使います。CLIの追加flagや環境変数による変更は導入しません。

| 項目 | 既定値 |
| --- | --- |
| 単一ファイル | 8 MiB（8,388,608 bytes） |
| 全ファイルの合計 | 64 MiB（67,108,864 bytes） |
| 異なるファイル数 | 1,024。入口も1件 |

本文のUTF-8バイト数を数え、コメント・空白・NUL・LF・CRLFも含めます。正規化や改行変換はしません。canonical pathが同じファイルは一度だけ課金し、ダイヤモンド状の依存でも再読込みしません。別pathのハードリンクは従来どおり別ファイルです。

読込みは「単一上限と合計残量の小さい方＋確認用1バイト」までに制限します。上限ちょうどならEOFを確認して受理し、次のバイトがあれば超過を診断します。ファイルサイズの事前情報だけには頼りません。超過・読込み失敗・不正UTF-8の本文はSourceMapへ登録せず、後続ファイルを読み続けません。

| 失敗 | 診断 |
| --- | --- |
| 入口の超過・読込み失敗 | 対象pathを示す。未登録の本文に架空のSourceId/Spanを付けない |
| import先の超過・読込み失敗 | import元のSourceIdと宣言Spanを示す |
| 読み込めた本文の構文超過 | その本文のSourceId/Span。単一ファイルCLIの匿名ソース契約は維持 |
| 出力先を指定したCLIの失敗 | 既存成果物を書き換えない |

同梱の`std:io`はファイル探索を行わない仮想ソースなので、このファイル予算には含めません。本文・出自・型同一性の観測は従来どおりです。`compile(&str)`・`modules::from_source`等へ既に渡されたメモリ入力もファイル読込み予算の対象外です。これらにも構文・式の深さ検査は適用します。埋込み側の入力受付量は呼出し前に制限できます。

```rust
use cerune_lang::modules::{load_with_limits, LoadLimits};
use std::path::Path;

let compilation = load_with_limits(
    Path::new("main.ceru"),
    LoadLimits {
        max_file_bytes: 1024 * 1024,
        max_total_bytes: 8 * 1024 * 1024,
        max_files: 64,
    },
);
```

0バイト上限でも空ファイルは受理できます。0ファイル上限は入口を拒否します。これらは読んだ本文の論理量であり、allocatorの容量、token/AST/IRの追加メモリ、OSのRSS、読込みの待ち時間を表しません。通常の親ディレクトリimportを禁止するsandbox機能も追加しません。


ファイルの探索も明示的なスタックで反復します。128段のimportの途中で末端のParserを呼ぶ際、祖先ファイルごとのRust呼出しフレームを積み重ねません。登録順は従来の深さ優先のままです。

## 検証と残件

`tests/modules.rs`に組み込んだ`tests/frontend_limits/mod.rs`で、子プロセスに10秒の上限を設け、括弧・型・block・配列・単項・二項・論理演算・field/indexの境界と超過を検証します。幅の広い配列、文字列・コメント中の記号、区切りだけでは数えられない再帰、式とblockの組合せも対象です。

ファイル検証は、UTF-8/CRLF、上限ちょうどのEOF、1バイト超過、個別/合計/件数の失敗、重複path、標準モジュール、不正UTF-8、診断の出自、CLI成果物の保持を扱います。[既存モジュールexample](../../examples/modules/README.md)と単一ファイルexampleも実行比較します。

[#135](https://github.com/Cerune-Lang/Cerune/issues/135)と[#153](https://github.com/Cerune-Lang/Cerune/issues/153)の構文・読込み上限を対象にします。#153の隔離用import制限、生成CのNDEBUG検査、CI供給元固定、継続fuzzingは別の残件です。後続の意味処理や合成ASTの資源制限は、Parser上限だけで完了扱いにしません。
