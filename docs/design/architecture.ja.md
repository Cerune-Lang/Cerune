# Ceruneコンパイラの設計

[English](architecture.en.md)

Ceruneは静的型付きの実験言語です。型・意味の決定と、実行表現への変換を観測可能に保ちます。[可観測性の契約](observability.ja.md)と[出力経路・ターゲット](targets.ja.md)が、観測と生成物の条件を定めます。

現在の実装と計画は次のとおりです。

| 状態 | 内容 |
| --- | --- |
| 実装済み | 完成済みCerune IR（HIR）の直接実行、bytecode VM、C・LLVM・QBE・WAT生成 |
| 実装済み | 非SSAのMIRの型・変換・検証・`emit-mir`・[独立実行](mir-executor.ja.md)、[MIR→Native生成](native-mir.ja.md) |
| 実装済み | [観測bundle](observation-bundle.ja.md)：sources・HIR・MIR・注釈付きASMを同じコンパイルから保存 |
| 実装済み | [SSA](mir-ssa.ja.md)の変換・直接実行・CLI／bundle・SSA→MIR／Native。有限例のLean検証も対応 |
| 実装済み | x86-64 LIRの変換・表示・保存・構造検証。直接実行は保留（[設計](lir-observation.ja.md)） |
| 設計済み・実装保留 | [定数畳み込みpass](ssa-constant-folding.ja.md)。最適化は暗黙に行わない |
| 計画・未実装 | IR・VM・Nativeの[build / release](owned-routes.ja.md)。C等はemit-onlyとして整理 |

## 設計原則

Ceruneは、洗練された実装と可観測性の両立を目指します。実装や変換が高度になっても、その境界と結果を観測可能に保ちます。

具体的には、次の原則に従います。

- 型に関する決定を目に見える予測可能なものにします。
- バックエンドに依存しない意味は、バックエンドへのloweringより前に解決します。
- バックエンド固有の決定は、明示的なlowering境界の内側で行います。
- emitterはCeruneの意味を再解釈せず、バックエンドIRを出力形式へ変換します。
- 最適化を行う場合は、実験対象となる明示的で観測可能なパスとして導入します。
- 生成する観測結果に、タイムスタンプやランダムな識別子などの偶発的な非決定性を含めません。

Cerune v0.1は、数値変換を暗黙に挿入したり、観測に有用な変換を隠したりしません。

## コンパイラ構成

共通frontendが意味を確定し、各実行器・生成経路へ渡します。

```text
Source → Lexer / Parser → AST → 共通frontend → Cerune IR (HIR)
                                               ├→ emit-ir / .ceir
                                               ├→ IR Executor: run / run-ir
                                               ├→ MIR変換・検証
                                               │    ├→ emit-mir / run-mir
                                               │    ├→ SSA → SSA実行／copy付きMIR → x86-64 LIR
                                               │    └→ x86-64 LIR → ASM → 自前Object
                                               ├→ Bytecode → emit-bytecode / run-vm
                                               └→ C / LLVM / QBE / WAT向けIR → emit-*
```

LIRはNative生成の段階です。`emit-lir`／`observe --lir`で観測できます。SSAから戻したMIRも同じLIR→ASM→Objectを通ります。`run-lir`の追加は[調査の結果、保留](lir-observation.ja.md)としました。

frontendは名前・型・文脈上の浮動小数点型を解決し、generic・enum/match・所有処理を共通展開します。[IR Executor](ir-executor.ja.md)は完成済みHIRの文・式を直接実行し、生成経路は確定済みの意味を対象の表現へ変換します。

### 構造上の不変条件

各段階の責務と識別子の意味を保ちます。

1. ASTからbackendへ直接進まず、共通の意味検証・型解決を済ませたHIRを使います。NativeはHIRからMIRへ変換した後にloweringします。
2. lowererは入力IRと出力IRを参照します。emitterは自身のbackend IRを読み、ASTや意味解析状態から意味を再決定しません。
3. backend固有のRust IRは内部実装です。公開する観測はHIR・MIR・SSAのテキストと生成成果物で、内部構造を安定したシリアライズ契約とはしません。
4. 最適化は暗黙に行わず、将来のpassも選択と変換過程を明示します。
5. 束縛にはコンパイル内で決定的なIDを付け、shadowing後も参照先を区別します。
6. HIRは`if`・`while`・`for`・`break`・`continue`を保持し、forの初期化・条件・本文・更新を分けます。MIR・bytecodeや各backendへの変換が分岐・合流・更新・後方辺・出口を具体化します。
7. HIRの文・式の`NodeId`はコンパイル内で一意です。要素の同一性を示すIDと、ソース位置を示す`Span`を混同しません。MIRのblock・命令IDは別の番号空間です。

Rustモジュールの配置は経路ごとに異なります。NativeはMIR→LIR→ASM、他の生成backendはHIR→backend IR→成果物へ変換します。

## Cerune IR

Cerune IRは、構文解析、意味検証、型の解決を終えたあとに生成される、型付きでバックエンドに依存しない表現です。

すべてのCerune IR式は、具体的な型に解決されています。

```text
bool
i8
u8
i16
u16
i32
u32
i64
u64
f32
f64
string
名前付きproduct type（直和型の展開結果を含む）
固定長配列・動的配列
```

`infer`はCerune IRが生成される前に解決されるため、実行時の型やバックエンドの型としては現れません。

AST、意味解析、Cerune IR、bytecodeは整数の種類を共通の`IntegerType`で表します。`I8`・`U8`・`I16`・`U16`・`I32`・`U32`・`I64`・`U64`を持ち、型名、符号、ビット数、最小値と最大値を取得できます。VMの値にも整数型を保持し、命令の型が一致することと結果の範囲を検査します。

接尾辞のない浮動小数点リテラルも、バックエンドへのloweringより前に解決されます。各バックエンドが文脈に基づく型推論を繰り返す必要はありません。

整数リテラルはlexerのtokenとASTでは10進数字の並びを保持します。意味解析が期待される整数型に対して範囲を検査し、Cerune IRを構築するときに確定済みの値へ変換します。これにより、`i64`の最大値を超える`u64`リテラルも扱えます。

整数変換の`i32(value)`と`convert<i32>(value)`は同じ`ConvertInteger`へ解決し、元の書式は`ConversionSyntax`で別に保持します。入力の型を変換先から推論し直さず、入力を一度だけ評価します。実装済みの8種類の整数型の全組み合わせを扱い、範囲外の変換は算術演算の桁あふれとは別のVMエラーになります。bytecodeの変換命令には変換前後の型と出自を残します。

浮動小数点を含む明示変換は`ConvertNumeric`へ解決します。共有の`NumericType`で整数・`f32`・`f64`を区別し、Cerune IRとbytecodeに変換元と変換先を残します。バックエンドIRの`NumericConversion`にも両方の型を保持し、emitterは入力の型を推論し直しません。整数同士の既存の観測表現は変更しません。

変換は、入力の計算が終わった時点の値を正確に保てる場合だけ成功します。範囲検査と逆変換による比較を使い、小数部分や精度の喪失を検出します。C・LLVMなどでは、範囲外の浮動小数点を整数へ変換する前に検査します。`i64`最大値を浮動小数点にすると2^63へ丸められるため、整数の上限は「最大値以下」ではなく、正確に表せる「最大値+1未満」で検査します。

浮動小数点同士では無限大とゼロの符号を保ち、型を変えるNaNは拒否します。整数への変換では無限大・NaNとマイナスのゼロも拒否します。同じ型への変換は元の値をそのまま返し、NaNの内部情報も変更しません。この場合、loweringで実行処理を省いてもCerune IRとbytecodeの明示変換は残します。これは変換の規則であり、通常の浮動小数点演算の丸めを禁止するものではありません。

現在のコード生成バックエンドは、8種類の整数型を64ビットの値として格納します。`u64`は最上位ビットも数値の一部なので、符号なしの比較・除算・右シフトを選びます。Cでは`uint64_t`、ほかの生成先では64ビットの格納型と符号なし命令を使います。8・16・32ビット整数の算術結果と整数同士の変換結果には、元の型の範囲を検査する`CheckIntegerRange`をバックエンドIRへ残します。浮動小数点から整数への変換の範囲検査は`ConvertNumeric`の処理に含めます。64ビットの演算自体にも従来の桁あふれ検査を適用します。

この方針は値の範囲と失敗条件を実装するためのもので、8・16・32ビット格納や外部ABIへの対応ではありません。配列・構造体も64ビット領域を使うため、現段階ではメモリ使用量は減りません。Cerune IRにある意味上の型と、バックエンドが選んだ格納型を混同しないことが重要です。

Cerune IRは、汎用的なマシンIRになることや、早い段階でSSA形式を課すことを目的としません。フロントエンドとバックエンドの境界を明確に保てる範囲で、Ceruneの意味を直接表します。

Cerune IRの文と式は、一つの通し番号による`NodeId`を持ちます。`emit-ir`では`#0`、`#1`のように表示します。親要素を子要素より先に、決定的なIR表示順で割り当てるため、同じCeruneのバージョンと同じ入力からは同じIDが得られます。

`NodeId`は一回のコンパイル結果の中で要素を参照するための値です。ソースを編集した場合やCeruneのバージョンが変わった場合まで同じ番号を保つ識別子ではありません。また、同じ`Span`を持つ複数のIR要素にも別々の`NodeId`を付けられます。これにより、今後一つの式が複数のbackend命令へ分解された場合も、位置だけに頼らず出自を記録できます。

型名と接尾辞は`IntegerType::ALL`から解決します。C・LLVM・QBE・WATでは必要な範囲検査を整数型の順序付き集合に集め、型ごとに一度だけ補助関数を出力します。これにより、型追加時の登録漏れを減らし、観測成果物の順序を決定的に保ちます。

## バックエンドへのlowering

### 短絡評価の論理式

ASTとCerune IRは`&&`・`||`を通常の二項演算とは別の`Logical`として保持します。左右とも`bool`であることをフロントエンドで検査し、右辺を実行する条件もCeruneの意味として確定します。定数の左辺で実行を省略できる場合も、右辺の名前解決・型検査とIR構築を省略しません。

bytecodeでは、左辺を取り出す条件付きジャンプと合流先へのジャンプに分解します。分岐命令には論理式の`NodeId`と左辺の`Span`を付け、右辺の命令は右辺自身の出自を保ちます。実行した右辺が失敗した場合、論理式全体ではなく失敗した処理の位置へ戻れます。

Cでは短絡評価を持つ論理式へ、WATでは`bool`を返す`if`へ変換します。LLVMとQBEでは、左辺の結果をコンパイラ生成の保存領域へ置き、右辺を実行する分岐でだけ更新して合流後に読み取ります。Windows/Linux x86-64では、MIRの一時値と条件分岐をLIRの保存領域・分岐へ変換します。いずれも右辺の評価を分岐の外へ持ち出しません。

これらの変換はHIR・MIR・生成物で観測します。実行履歴とは区別します。

### 剰余とビット演算

ASTとCerune IRは剰余、AND、OR、XOR、左右のシフト、単項のビット反転を区別し、元の整数型を保持します。bytecodeにも型付き命令と式の`NodeId`・`Span`を残します。VMは左シフトを広い整数で計算してから元の型の範囲を検査し、シフト量の違反や剰余の0除算を別のエラーとして扱います。

コード生成側は整数専用の`IntegerBinaryOp`と元の`IntegerType`を、各バックエンドIRの`IntegerBinary`へ渡します。単項`~`は符号付きなら`-1`、符号なしなら元の型の最大値とのXORへ下げます。64ビットで格納していても、`~0u8`の結果は255です。EmitterはCerune IRの解釈や型推論を繰り返しません。

C・LLVM・QBE・WATは、必要な演算と型の組を順序付き集合に集め、各補助関数を一度だけ出力します。Cでは式ごとの一時変数とコンマ演算子で左右の評価順を守り、式を短絡評価やループの外へ移動しません。Windows/Linux x86-64はレジスタ上の演算と明示的な検査分岐へ下げます。

シフト量は元の型の幅で先に検査します。左シフトは入力に許される上下限を求めてから実行し、捨てられたビットを事後検査で見逃すことを避けます。Cでは負数のシフトに依存せず、検査済みの乗算で左シフトを実現します。右シフトの符号も出力先の偶然の動作へ委ねません。符号付き最小値の`% -1`は、除算命令の桁あふれを起こさず0を返します。

### 各出力先への変換

NativeはMIRからx86-64 LIRへ、他の生成バックエンドはHIRから各バックエンド固有のRust表現へloweringします。

Cerune IRで一つの整数演算として見える式は、backend loweringで演算本体と桁あふれ検査へ分かれる場合があります。検査を外部ツールの偶然の動作へ任せず、backend内部表現では検査付き整数演算または明示的なtrap条件として保持します。生成成果物ではhelper呼び出し、overflow flagの分岐、`unreachable`など、対象に適した形として観測できます。

現在の出力経路と実装上の境界は次のとおりです。

| 出力経路 | バックエンド内部表現 | 出力される成果物 |
| --- | --- | --- |
| C | C IR | `.c` |
| LLVM | LLVM IR表現 | `.ll` |
| QBE | QBE IR表現 | `.ssa` |
| WebAssembly | WAT指向の命令IR | `.wat` |
| Windows/Linux x86-64直接アセンブリ | MIRから変換したx86-64 LIR | `.s` |
| ネイティブオブジェクト | 共通ASMの読み取り・命令符号化・ELF/COFF生成 | `.o` / `.obj` |
| Cerune bytecode | `BytecodeProgram` | `.cebc` |

バックエンドIRには、Cerune IRに含めるべきでない決定を表現できます。

例を示します。

- LLVMとQBEの一時値およびバックエンド命令
- WATのスタックマシン命令およびローカル変数
- C固有の型および出力形式
- x86-64のスタックスロット、フレームサイズ、定数、レジスタ、ABI操作
- bytecodeのスロットおよびVM命令

これらの表現は現在、公開されたシリアライズ形式ではなく、安定したCLI契約にも含まれません。

### ソース位置とbytecode命令の出自

Cerune IRの文と式は、対応するソースコードのUTF-8バイト範囲を保持します。範囲は開始位置を含み、終了位置を含みません。行番号と列番号は表示時にこの範囲から求めます。

各bytecode命令は命令本体とは別に、次のいずれかの出自を保持します。

- `Source { node_id, span }`: Cerune IRの文または式から生成された命令
- `Synthetic`: ソースコード上に直接対応する箇所を持たない、コンパイラ生成の命令

`Synthetic`は追跡情報の欠落を意味しません。コンパイラ生成であることを明示する値です。

`node_id`は命令を生成したCerune IR要素を示します。一つのIR要素が複数の命令へloweringされた場合、それらの命令は同じ`node_id`を持てます。`span`は診断で強調する範囲であり、必ずしもIR要素全体の範囲とは限りません。たとえば、入れ子の配列要素代入から生成される各境界検査は、同じ代入文の`node_id`と、それぞれ異なる添字の`span`を持ちます。

VMは実行エラーをbytecode命令番号で報告します。`run_vm`はその番号から命令の出自を解決し、Cerune IRの`NodeId`と、利用可能な場合はソース位置を実行エラーへ関連付けます。この出自情報は現在の内部表現であり、`emit-bytecode`のテキスト形式には含めません。

## 観測境界

現在はHIR、MIR、各経路の生成物を観測できます。実行結果・実行履歴とは区別します。

### 観測1: 解決済みのCeruneの意味

`emit-ir <file> [-o <output.ceir>]`は、構文・意味検証、式と文脈上の浮動小数点型の解決を終えた、backend非依存のHIRを出力します。「ソースをどう解釈したか」を示し、ABI・物理的な値配置・stack machine・対象命令の選択は含めません。

### MIR: 明示的な実行手順

`emit-mir <file> [-o <output.txt>]`は、型付き局所値・一時値、block・分岐、所有操作、元の出自を持つ非SSAのMIRを出力します。`Cerune MIR v0.1`は観測テキストであり、安定した配布形式やload可能なImageではありません。`run-mir`は同じ表現を独立実行する操作です。

### 観測2: 出力成果物

生成物は「選択した経路・ターゲットが、確定済みの意味をどう表現したか」を示します。

| コマンド | 成果物 | 指定 |
| --- | --- | --- |
| `emit-c` | `.c` | `-o`で保存 |
| `emit-llvm` | `.ll` | `--target`、`--annotate-origins`、`-o` |
| `emit-qbe` | `.ssa` | `--target`、`-o` |
| `emit-wat` | `.wat` | `-o`で保存 |
| `emit-asm` | `.s` | `--target`、`--annotate-origins`、`-o` |
| `emit-obj` | `.o` / `.obj` | `--target`・`-o`必須。出自注釈も指定可 |
| `emit-bytecode` | `.cebc` | `-o`で保存 |

各コマンドは`<file>`を入力に取ります。ターゲットが必須になる機能や省略時の扱いは[CLI](../reference/cli.ja.md)で定めます。個別の観測には`emit-*`を使います。[`observe`](observation-bundle.ja.md)は既存の観測結果を同一コンパイルのbundleへ保存する操作で、新しい意味表現や実行経路ではありません。

### 内部バックエンドIRは観測契約ではない

内部のRust構造は、v0.1の安定したserialization契約に含めません。`emit-lir`は[バージョン付き観測テキスト](lir-observation.ja.md)であり、load可能な配布形式ではありません。

## コード生成

Ceruneは、最適化そのものではなく、観測できない暗黙のソースレベル最適化を避けます。

バックエンドへのloweringでは、対象表現に必要な機械的変換に加えて高度な変換も行えます。ただし、観測に有用な構造が失われる場合は、その変換を明示的で観測可能なパスとして扱います。

正当なloweringの例を示します。

- 型付きLLVM命令またはQBE命令の選択
- Cerune式からWebAssemblyスタック命令への変換
- Ceruneの値からCの型および式への対応付け
- Direct ASMのスタックスロット割り当ておよび定数の実体化
- Ceruneの演算からbytecode命令へのlowering

将来最適化を導入する場合は、出力処理の内側に隠さず、名前と境界を持つ明示的なパスにします。

## ツールの責務

Cerune、Tint*、Whitebaseは異なる責務を持ちます。

### Cerune

Ceruneはコンパイラによる変換と出力を担当します。

```text
Parse
  ↓
Resolve
  ↓
Cerune IR
  ↓
Lower
  ↓
Backend IR
  ↓
Emit
```

Ceruneは、観測可能なコンパイラ成果物を定義し生成します。

### Tint*

Tint*は、Ceruneのための視覚的な開発・観察環境です。

コンパイラの意味を重複して実装せず、Ceruneが公開するCLIの観測結果を利用します。ソースと生成された表現を対話的に調べ、比較しやすくすることがTint*の役割です。

### Whitebase

現在のWhitebaseは、組み込みのRust・C++・Assembly演算を実行・計測・比較します。Ceruneのソースや生成物を受け取り、外部コンパイラでビルドして実行する連携は未実装です。

連携時は、出力された成果物を実験への入力として利用し、経路選択、ビルド、実行、計測、比較と、それらに影響する外部の選択の記録をWhitebase側が担当する方針です。以下は現在の実装図ではなく、連携時の責務を示します。

```text
Cerune source
      ↓
Cerune
      ↓
Observation artifact
      ↓
Whitebase
  - select build route
  - invoke external tools
  - run
  - measure
  - compare
```

WhitebaseはCerune内部のRust IRに依存せず、Ceruneを外部ツールの境界として扱います。

Ceruneの回帰テストは、型・診断・生成物・実行結果が言語の規則を守るか検証します。外部コンパイラを使った生成コードの検証も、この目的ならCeruneの開発用テストに含められます。一方、利用者がツールチェーンや条件を選び、実験を保存・比較する機能は利用側の責務です。テストの保存形式や比較方法を一種類に固定するものではありません。

「生成できる」「ビルドできる」「実行できる」と実行権限は別々に扱います。[生成物を利用する側との境界](targets.ja.md#生成物を利用する側との境界)を参照してください。この整理のために新しい公開APIを追加したり、文字列などの言語機能を連携の完成まで待たせたりする必要はありません。

## 再現性

観測成果物は、直接比較できるときに最も有用です。

同じCeruneのバージョン、ソース入力、出力経路、ターゲット、ターゲット機能、明示的なオプションに対して、Ceruneは可能な限り決定的なテキスト観測結果を生成します。

タイムスタンプ、ランダムな識別子、環境依存のメタデータなどの偶発的な値は、それ自体が実験対象でない限りCeruneの観測結果に含めません。

外部ツールチェーンの出力はこの保証の対象外です。Whitebaseなどの利用側が記録します。

## 対象外と今後の検討事項

現在の設計では、次のものを必要としません。

- バックエンド固有のRust IRを公開するシリアライズ形式
- 個別`emit-*`やbundleとは別の、意味表現を重複定義する観測API
- すべてのバックエンドへのSSAの強制（MIRのSSA化は将来の明示的な選択肢）
- 暗黙の最適化
- emit-only経路の外部コンパイラやランタイムの統括（Cerune-ownedのbuild計画とは区別）
- Cerune内部でのベンチマークまたは性能測定

将来の検討事項には次のものがあります。

- 追加の観測境界を持つ明示的な最適化パイプライン
- 具体的な用途が生じた場合の、任意のバックエンドIR観測
- 観測bundleにObject・他backend・変換前後の比較を追加
- IR・VMの完成成果物としての、検証・load可能なImage。形式と検証器は[build / releaseの計画](owned-routes.ja.md)で整理

これらの機能は、次の中心原則を保てる場合にのみ追加します。

> Ceruneは、変換をより観測しやすく、より説明しやすいものにします。
